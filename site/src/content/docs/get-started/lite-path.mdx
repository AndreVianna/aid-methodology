This page shows you how to make a small, well-scoped change with a [shortcut](/reference/glossary/#shortcut), which plans the work in one run and waits for your approval.

This way of working is the [lite path](/reference/glossary/#lite-path). A shortcut is a command that names your change, such as `/aid-fix` for a bug or `/aid-create api` for a new endpoint. Instead of walking each phase with you, it runs the Describe, Define, Specify, Plan and Detail phases in one pass. For broad or risky work, use the full phases in [Your first work](/get-started/first-work/).

## Two ways in

- **Name your change with a shortcut.** If you know what you are changing, run the matching shortcut: `/aid-fix` for a bug, `/aid-create api` for a new endpoint, `/aid-update ui` for a UI change.
- **Ask `/aid-triage` when you are not sure.** Describe your change in one sentence. [`/aid-triage`](/reference/glossary/#aid-triage) suggests the matching shortcut. For broad, multi-part or unclear work, it suggests `/aid-describe` instead. It suggests one next step and stops. It does not run the change and it creates no work folder. If it cannot find one confident match, it sends you to the full phases.

## The shortcut engine

Each shortcut that plans work (such as `/aid-fix`) hands over to the same [shortcut engine](/reference/glossary/#shortcut-engine). A few skills are hand-written and do not use it; they are listed below. The engine runs these states in order:

```
INTAKE -> CAPTURE -> SPEC -> PLAN -> DETAIL -> GATE -> APPROVAL-HALT
```

The engine skips no phase. It gathers the information for each phase in one run. CAPTURE, SPEC, PLAN and DETAIL run without a checkpoint after each one. It can ask whether this is new work or a continuation at INTAKE, and a gap that matters in CAPTURE. It stops for your approval at the end.

GATE then grades every document the engine wrote. It repeats review and fix until each document meets the [minimum grade](/reference/glossary/#grading), which is the `minimum_grade` setting (the shipped default is `A`). APPROVAL-HALT then shows you the work and stops.

The engine never builds anything. You start `/aid-execute` yourself after you approve.

Each run writes one new work. If works already exist, the engine first asks whether this is a new work or a continuation of an existing one. If you pick a continuation, it sends you to that work's own command. The engine does not resume an interrupted run when you run the shortcut again.

## Make a change with a shortcut

1. **Run a shortcut, or ask `/aid-triage` first.** Describe your change in a sentence or two:

   ```
   /aid-fix "login crash on special characters"
   ```

   Other shortcuts take a kind as the first word, such as `/aid-create api "an /orders endpoint"` or `/aid-update config`. Each kind is a row of the [shortcut catalog](https://github.com/AndreVianna/aid-methodology/blob/master/canonical/aid/templates/shortcut-catalog.yml).
2. **Answer the gap question, if asked.** The engine works out the rest on its own.
3. **Review the work at the approval halt.** The engine shows the files it wrote, the grades from GATE, and the tasks. Read them, then approve.
4. **Execute.** Run this command once for each task:

   ```
   /aid-execute work-001 task-001
   ```

   Execute carries out the task and gives it a quick check. The delivery gate grades the delivery against the minimum grade. You can leave out `work-001` when you have only one work.

## What a shortcut work looks like on disk

A shortcut writes a flat work: one implicit delivery, with no `deliveries/` folder.

```
.aid/
  works/
    work-NNN-name/
      STATE.yml          # work lifecycle; each task's state is kept here
      REQUIREMENTS.md    # section 11 holds the single feature section
      tasks/
        task-NNN/
          DETAIL.md      # the task definition
```

It has no `PLAN.md` and no [`STATE.yml`](/reference/glossary/#state-file) for each task. The full phases write a nested layout instead. It is described in [Your first work](/get-started/first-work/).

## Shortcuts and the full phases

| | Shortcut (lite path) | Full phases |
|--|----------------------|-------------|
| Start with | A shortcut such as `/aid-fix`, or a suggestion from `/aid-triage` | `/aid-describe`, after `/aid-discover` for an existing project |
| Best for | Small, low-risk, well-bounded work | Large, risky or poorly understood work |
| Phases | One engine run covers Describe to Detail | One run for each phase |
| Files | `REQUIREMENTS.md` and `tasks/task-NNN/DETAIL.md` | `REQUIREMENTS.md`, `PLAN.md`, and `deliveries/delivery-NNN/tasks/task-NNN/DETAIL.md` |
| Approvals | One, at the halt | One at the end of each phase |

A shortcut does not lower the quality bar. GATE grades every document, and `/aid-execute` quick-checks every task and the delivery gate grades the delivery.

## The shortcut doorways

These family shortcuts are thin doorways into the engine: `/aid-fix`, `/aid-create`, `/aid-update`, `/aid-refactor`, `/aid-remove`, `/aid-deprecate`, `/aid-migrate` and `/aid-experiment`. Run one bare, or give a kind as the first word of its argument, as in `/aid-create api`.

Other shortcuts, such as `/aid-review`, `/aid-research` and `/aid-document`, are hand-written skills, not doorways. The [Skills reference](/skills/) lists every skill. The [shortcut engine definition](https://github.com/AndreVianna/aid-methodology/blob/master/canonical/aid/templates/shortcut-engine.md) describes each state in full.
