This page lists the documents in `.aid/knowledge/`. For what the Knowledge Base is and how to build it, see [The Knowledge Base](/guides/knowledge-base/).

## How many documents, and who decides

The shipped templates contain **14 standard documents**. Discovery uses them as the default set, one document per template file.

Your project's set does not have to match. `/aid-discover` proposes a set from the project's domain, you confirm it, and it is stored as a list in `.aid/settings.yml` under `knowledge.doc_set`. A project can add documents, such as a roadmap or a decision log, and drop ones that do not apply. Tools read this list, not a built-in count.

Each entry in the list has three fields separated by `|`:

```yaml
knowledge:
  doc_set:
    - architecture.md|aid-researcher-architecture|required
    - infrastructure.md|aid-researcher-quality|conditional:project has deployment or CI configuration
```

| Field | Meaning |
|---|---|
| File name | The document's name inside `.aid/knowledge/` |
| Owner | Who writes it: one of five `aid-researcher` slots, or `skill-self` when the skill generates it |
| Presence | `required`, or `conditional` with an optional hint after a colon |

Commas are not allowed inside any field, because the list is read back as comma-separated text. See [Settings reference](/reference/settings/).

Older notes call this key `discovery.doc_set`. The key is `knowledge.doc_set`; the old name is still read as an alias.

## The standard documents

All of these are written by a research agent from the code, then reviewed. The "Written by" column is the researcher slot named in the doc set.

| File | What it holds | Written by |
|---|---|---|
| `project-structure.md` | Repository layout and what each top-level folder is for | Scout |
| `external-sources.md` | Registry of outside documentation, vendor specs and reference URLs | Scout |
| `architecture.md` | Patterns, levels, data flow and module boundaries: how the system hangs together | Architecture |
| `technology-stack.md` | Languages, runtimes, frameworks, build tools and test tooling | Architecture |
| `module-map.md` | For each module: purpose, dependencies, owners and entry points | Analyst |
| `coding-standards.md` | Conventions mined from the real code: naming, formatting, idioms, process rules | Analyst |
| `schemas.md` | Data schemas, artifact shapes, data flow and how entities relate | Analyst |
| `pipeline-contracts.md` | Public interfaces, request and response shapes, protocol contracts | Integrator |
| `integration-map.md` | What the project consumes and exposes, and how its parts talk | Integrator |
| `domain-glossary.md` | Project vocabulary with definitions | Integrator |
| `test-landscape.md` | Test frameworks, what is covered, and the gaps | Quality |
| `tech-debt.md` | Open technical debt, tagged by severity, with remediation paths | Quality |
| `infrastructure.md` | Distribution, environments, CI/CD, source-control conventions and tooling | Quality |
| `feature-inventory.md` | The feature list with status (shipped, partial or deferred) | The skill itself |

The researcher slots are `aid-researcher-scout`, `aid-researcher-architecture`, `aid-researcher-analyst`, `aid-researcher-integrator` and `aid-researcher-quality`. They are five roles of the one `aid-researcher` agent. See [Agents reference](/reference/agents/).

Each of these documents opens with frontmatter that gives its purpose (`objective`), a one-line `summary`, and the files it was built from (`sources`). The index and the freshness check are built from those fields.

## Other files in the folder

These are not part of the standard set, but you will see them.

| File | What it holds | Written by |
|---|---|---|
| `PROJECT.md` | The one-page project card, read first in every session | By hand, from the `project-card.md` template. No skill writes it for you. |
| `INDEX.md` | A table of every document with its objective and summary | Generated by `build-kb-index.sh`; never edit by hand |
| `README.md` | Completeness tracker for the confirmed document set | The discovery skill |
| `STATE.md` | Discovery run state: grade, approval, open questions, review history | `/aid-discover` creates it (from a template, if missing); `/aid-summarize` and other phases update it |
| `kb.html` | Single-page visual tour of the KB | `/aid-summarize` |

Beyond the standard set, a project can have extra documents. The AID repository's own KB, for instance, also has a decision log, authoring conventions, a roadmap and a backlog. For a new project, the `/aid-describe` interview can author `domain-glossary.md`, `architecture.md`, `coding-standards.md`, `technology-stack.md` and, when you confirm real decisions, `decisions.md`.

Generated working files also appear outside the folder, in `.aid/generated/`: a project index and a metrics file. Numbers such as line counts live there, not in KB documents.

## Document labels

Each document carries two labels in its frontmatter.

| Label | Values | Effect |
|---|---|---|
| `kb-category` | `primary`, `extension`, `meta` | Primary and extension documents are reviewed. Meta documents (index, readme, state) are process files and are exempt. |
| `source` | `hand-authored`, `generated`, `forward-authored` | Says how the document was produced. Forward-authored documents come from the greenfield interview. |

## Rules every document follows

- It states current facts only. No dates, no cycle numbers, no history.
- It cites a file path plus a symbol or heading, never a bare line number.
- It never names a work or a work folder.
- It holds no measured numbers such as line counts, because they go stale.
