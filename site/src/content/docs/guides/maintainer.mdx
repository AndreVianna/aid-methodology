This page shows maintainers of AID how to cut a release and how to regenerate the per-tool agent trees.

## Who this is for

This page is for **maintainers and contributors to AID itself**: people who cut releases or change the [canonical](/reference/glossary/#canonical) source and need to keep the five per-tool agent trees and the [shared payload](/reference/glossary/#shared-payload) in sync.

If you use AID in your own projects, you do not need this page. Read the [pipeline guide](/guides/pipeline/) instead.

## Cut a release

The primary release path is a single pushed `v*` tag that triggers the `release.yml` CI
workflow. The manual `release.sh` path is a fallback for when CI is not available.

The maintainer-only skill `/release-aid <level>` runs the whole sequence for you. The level is `major`, `minor`, `patch` or `beta`. The skill lives only in this repository, at `.claude/skills/release-aid/`, and is not shipped to adopters. The steps below are the manual runbook.

### How releases work

A single pushed `v*` tag triggers `release.yml`, which runs these jobs:

1. **gate**: re-runs the version-sync check, the render-drift check, the canonical helper suites and the generator self-tests on the tagged commit.
2. **github-release**: runs only after the gate passes. It runs `release.sh`, which builds the shared payload, the agents-only tool artifacts, the `aid-cli` bundle, two install-core library files and `SHA256SUMS`, and creates the GitHub Release with all assets.
3. **npm-publish**: publishes `aid-installer` to npm with OIDC provenance. It runs only when the repository variable `NPM_ENABLED` is `true` and the version is not a pre-release.
4. **pypi-publish**: publishes `aid-installer` to PyPI through Trusted Publishing (OIDC). It runs only when the repository variable `PYPI_ENABLED` is `true`.

The npm and PyPI jobs both wait for the GitHub Release job and run in parallel. The GitHub Release artifacts, npm, PyPI and the [offline bundle](/reference/glossary/#offline-bundle) all come from the same tag in one workflow run.

A pre-release tag, such as `v2.2.3-beta.1`, creates a GitHub Release marked as a pre-release. It also publishes to PyPI, but only when `PYPI_ENABLED` is `true`. The npm job is skipped.

### Prerequisites

Before running either release path:

- **`VERSION` file is set to the intended release version.** The gate fails unless the tag,
  `VERSION`, `packages/npm/package.json` and `packages/pypi/pyproject.toml` all agree
  (for a pre-release, the npm file is exempt).
- **Clean, passing CI on master.** Push the tag only from a commit where `test.yml` is
  green.
- **Render-drift clean.** `profiles/` must be in sync with `canonical/`. See the
  [Regenerate trees](#regenerate-the-host-tool-treesprofiles) section below. The gate
  re-runs the check and fails the workflow if they diverge.
- **No tag `v<VERSION>` on another commit.** On the manual path, `release.sh` fails with exit code `4` if the tag already points at a different commit.
- **`gh` CLI authenticated.** `gh auth status` must show write access to the repo.

```bash
# Quick precondition check
git status
git tag -l "v$(cat VERSION)"
gh auth status
python .claude/skills/generate-profile/scripts/run_generator.py && git diff --exit-code -- profiles/
```

### Primary path (tag-triggered CI) and manual path (release.sh)

#### CI path (primary)

<Steps>
1. **Verify preconditions**

   ```bash
   git status                                     # must be clean
   git tag -l "v$(cat VERSION)"                   # must print nothing
   gh run list --workflow test.yml --limit 5      # confirm CI is green on master
   python .claude/skills/generate-profile/scripts/run_generator.py && git diff --exit-code -- profiles/
   ```

2. **Dry run (optional)**

   Use the `workflow_dispatch` trigger with `dry_run: true` to build and validate without
   publishing:

   ```bash
   gh workflow run release.yml --ref master -f ref="v$(cat VERSION)" -f dry_run=true
   gh run watch   # monitor progress
   ```

3. **Push the version tag**

   ```bash
   git tag "v$(cat VERSION)"
   git push origin "v$(cat VERSION)"
   ```

   This starts the `release.yml` run: gate, then github-release, then npm-publish and
   pypi-publish in parallel.

4. **Monitor the workflow**

   ```bash
   gh run watch
   ```

   On success, the GitHub Release is live and the package registries are updated. On any
   failure, see [Recovery and idempotency](#recovery-and-idempotency).
</Steps>

#### Manual path (release.sh)

Use `release.sh` directly when you need to cut a release outside of CI (for example, a
hotfix). It produces the same GitHub Release assets as the CI path but does **not**
publish to npm or PyPI.

<Steps>
1. **Verify preconditions**

   Run `--dry-run` to validate without creating a release. It runs the generator first, so
   review and commit any files it changes:

   ```bash
   bash release.sh --dry-run
   ```

   Expected output:

   ```
   release.sh: version=X.Y.Z  tag=vX.Y.Z
   release.sh: verifying render state (python3 .claude/skills/generate-profile/scripts/run_generator.py) ...
   release.sh: checking for render drift (git diff -- profiles/) ...
   release.sh: render state is clean.
   release.sh: staging dir: .aid/.temp/release-X.Y.Z
   release.sh:   done: aid-shared-vX.Y.Z.tar.gz
   release.sh:   done: aid-claude-code-vX.Y.Z.tar.gz
     ...
   release.sh:   done: aid-cli-vX.Y.Z.tar.gz
   release.sh: SHA256SUMS written:
   release.sh: --dry-run: staging complete. Tarballs and SHA256SUMS are in:
     .aid/.temp/release-X.Y.Z
   ```

   Common failures:

   | Failure | Message | Fix |
   |---------|---------|-----|
   | Dirty worktree | `working tree has uncommitted changes` | `git stash` or commit the changes |
   | Render drift | `profiles/ is out of sync with canonical/` | Run the generator and commit (see [Regenerate trees](#regenerate-the-host-tool-treesprofiles)) |
   | Version mismatch | `--version X does not match VERSION file (Y)` | Drop `--version` or update `./VERSION` |
   | Tag at another commit | `Git tag vX.Y.Z already exists at a different commit` (exit `4`) | See [Recovery and idempotency](#recovery-and-idempotency) |

2. **Inspect staged artifacts**

   After a successful dry run:

   ```bash
   ls -lh ".aid/.temp/release-$(cat VERSION)/"
   ```

   Verify the shared payload, the five tool artifacts, the `aid-cli` bundle, two lib files,
   and `SHA256SUMS` are present. Spot-check an artifact:

   ```bash
   tar -tzf ".aid/.temp/release-$(cat VERSION)/aid-claude-code-v$(cat VERSION).tar.gz" | head -20
   cd ".aid/.temp/release-$(cat VERSION)/"
   sha256sum --check SHA256SUMS        # Linux
   shasum -a 256 -c SHA256SUMS         # macOS
   ```

3. **Create a draft release**

   ```bash
   bash release.sh --draft
   ```

   This calls `gh release create "v<VERSION>" --title "AID v<VERSION>" --draft` with all
   assets attached. Open the draft URL on the GitHub web UI, verify all assets and release
   notes, then publish.

   To supply release notes:

   ```bash
   bash release.sh --draft --notes-file /path/to/RELEASE-NOTES.md
   ```

4. **Publish the draft**

   From the GitHub web UI: open the draft release → verify assets and notes → click
   **Publish release**. Or from the CLI:

   ```bash
   gh release edit "v$(cat VERSION)" --draft=false
   ```
</Steps>

### What a release produces

`release.sh` (invoked by the CI workflow) stages artifacts under
`.aid/.temp/release-<VERSION>/` and uploads them to the GitHub Release:

**One shared payload:** `aid-shared-v<VERSION>.tar.gz`. It holds `aid-payload.conf` (the version),
`skills/` (a byte-for-byte copy of `canonical/skills/`) and `runtime/` (a byte-for-byte copy of
`canonical/aid/`, `rules.md` included).

**Five tool artifacts, agents only:**
- `aid-claude-code-v<VERSION>.tar.gz`
- `aid-codex-v<VERSION>.tar.gz`
- `aid-cursor-v<VERSION>.tar.gz`
- `aid-copilot-cli-v<VERSION>.tar.gz`
- `aid-antigravity-v<VERSION>.tar.gz`

Each holds `aid-tool.conf` and that tool's agents folder, and nothing else.

**`aid-cli-v<VERSION>.tar.gz`** — the `aid` CLI bundle (bootstrapped by `install.sh` /
`install.ps1` and by `aid update self`).

**Two install-core library files:**
- `aid-install-core.sh` — Bash install-core library sourced by `install.sh`.
- `AidInstallCore.psm1` — PowerShell install-core module imported by `install.ps1`.

**`SHA256SUMS`** — one `<64-hex>  <filename>` line per asset, sorted by filename.

Archive members have no leading `./` and no wrapping directory. A user needs the shared payload
plus the artifact of each tool they install, all at one version. No artifact should contain any
other member.

**npm:** `aid-installer` published at the version from `packages/npm/package.json`.

**PyPI:** `aid-installer` published at the version from `packages/pypi/pyproject.toml`.

### Recovery and idempotency

<Aside type="caution">
**Read this section before you re-run a failed release.** The npm-publish and pypi-publish jobs skip a version that is already published. A re-run of `release.sh` for the same commit refreshes the assets of an existing GitHub Release.
</Aside>

**A dry run is safe to re-run.** `--dry-run` never creates a tag and never creates a release.

**If the CI workflow fails after the tag is pushed,** fix the cause, then start the workflow again for the same tag:

```bash
gh workflow run release.yml --ref master -f ref="v$(cat VERSION)"
```

**If the tag points at the wrong commit,** delete it locally and on the remote, fix the cause, and tag again:

```bash
git tag -d "v$(cat VERSION)"
git push origin ":refs/tags/v$(cat VERSION)"
git tag "v$(cat VERSION)" && git push origin "v$(cat VERSION)"
```

If a GitHub Release was already created from the wrong commit, delete it on GitHub before you tag again.

**Staging directory cleanup:** the staging directory at `.aid/.temp/release-<VERSION>/`
is gitignored. Delete it when you do not need it:

```bash
rm -rf ".aid/.temp/release-$(cat VERSION)/"
```

### Flag reference (release.sh)

```bash
bash release.sh [--version X.Y.Z] [--sign] [--draft] [--prerelease]
                [--dry-run | --stage-only [--out DIR]] [--notes-file FILE] [-h|--help]
```

| Flag | Default | Description |
|------|---------|-------------|
| `--version X.Y.Z` | content of `VERSION` file | Release version. Must match `VERSION` file; fails on mismatch (exit 3). |
| `--sign` | off | Emit a detached signature over `SHA256SUMS`. Signing is deferred, so the script exits with an error. Do not use it. |
| `--draft` | off | Create the GitHub Release as a draft, so you can review it before you publish. |
| `--dry-run` | off | Assemble the artifacts and `SHA256SUMS`, then stop before `gh release create`. Runs the generator first. No network I/O. |
| `--stage-only` | off | Stage the artifacts from the working tree as it is. Skips the clean-tree, tag, render and network checks. |
| `--out DIR` | `.aid/.temp/release-<VERSION>` | Staging directory for `--stage-only`. Must be empty. |
| `--prerelease` | off | Mark the GitHub Release as a pre-release, so `/releases/latest` skips it. |
| `--notes-file FILE` | generated stub | Release notes body passed to `gh release create`. |
| `-h`, `--help` | — | Print help and exit 0. |

**Exit codes:**

| Code | Meaning |
|------|---------|
| `0` | Success (dry-run: staging complete; live: release created). |
| `1` | General failure (dirty worktree, render-drift, `gh` error). |
| `2` | Usage / argument error. |
| `3` | Version mismatch (`--version` does not match `VERSION` file). |
| `4` | The git tag already exists at a different commit. |

## Regenerate the host-tool trees/profiles

AID generates one agents-only tree per host tool (`profiles/claude-code/`, `profiles/codex/`,
`profiles/cursor/`, `profiles/copilot-cli/`, `profiles/antigravity/`) from `canonical/agents/` and
the per-tool descriptors (`profiles/*.toml`). Each tree holds the agents and `aid-tool.conf`, and
nothing else. The skills and runtime are not rendered: `release.sh` copies them byte-for-byte from
`canonical/` into the shared payload. This section explains how to keep the trees in sync.

### When to run

Run the generator any time you edit a canonical agent, skill, runtime file, or template, and before
you commit. Also run it to confirm the trees are in sync after a manual edit.

The render-drift CI convention requires committed `profiles/` content to match a fresh render. The
`release.yml` gate re-runs this check and fails the workflow if they diverge, so unclean profiles
block releases. See the [Cut a release → Prerequisites](#prerequisites) section above.

### What it does

`run_generator.py` runs these steps in order:

| Step | What happens |
|------|--------------|
| **VALIDATE** | Reads each `profiles/*.toml` and checks its keys. A bad descriptor stops the run. |
| **RENDER** | Wipes each `profiles/<tool>/` and renders that tool's agents and `aid-tool.conf` from `canonical/agents/`. |
| **VERIFY** | The deterministic check must pass, or the run fails. The advisory check prints how many files it checked and how many warnings it found, and never fails the run. |
| **DOGFOOD RESYNC** | Runs `sync_dogfood.py`. It runs `release.sh --stage-only` to build the artifacts from the working tree, then `aid update --from-bundle` to refresh this repo's own install: `.agents/skills/`, `.claude/skills/aid-*`, `.aid/runtime/`, the agents, and the `AGENTS.md` and `CLAUDE.md` regions. |

The dogfood resync can change files outside `profiles/`, so a run is not finished until you have
reviewed and committed everything it changed.

### Run it

```bash
python .claude/skills/generate-profile/scripts/run_generator.py
git status
```

Commit the changes the run produced. CI checks only the profile trees, with:

```bash
git diff --exit-code -- profiles/
```

The shared skills and runtime are checked byte-for-byte against `canonical/` by the
dogfood byte-identity test in the canonical helper suites.

### Verify and report

When `run_generator.py` completes, check the output for:

- **`VERIFY (deterministic): PASS`.** If this check fails, the run stops with an error. Do not commit.
- **`VERIFY (advisory): checked=N warnings=N`.** Read the warnings. Advisory warnings do not fail the run.
- **`Done. Profile trees regenerated and dogfood trees resynced.`** This line ends a successful run.

Confirm the scope of the change with:

```bash
git diff --stat -- profiles/ .agents/ .claude/skills/ .aid/runtime/
```

Only the profile trees and the dogfood install should change. Nothing under `canonical/` changes
during a run, so a diff there means an edit was made by hand.
