This page introduces the ideas behind AID and links to each Concepts page, so you can read the design before you look up facts.

[AID](/reference/glossary/#aid), short for AI Integrated Development, is a way to build software in which you and AI agents work through every phase together. You are the pilot and the AI is the suit. Each Concepts page answers one question. For lists of commands, settings and files, see the [Reference](/reference/overview/) section.

## Philosophy

### Waterfall plus AI

Understand → Specify → Plan → Build → Verify → Ship.

This is the Waterfall sequence, and AID follows it on purpose.

AID keeps the sequence and has AI agents do the heavy work in each phase. That changes what going back costs:

- **Discovery is done by an agent.** `/aid-discover` maps an existing codebase and drafts a structured Knowledge Base, which you review.
- **Specification is grounded.** `/aid-specify` proposes a design from the Knowledge Base and the code, and you decide.
- **Going back is a defined step.** A feedback loop sends a finding to an earlier phase, so filling a knowledge gap does not mean starting over.
- **Documents can be kept current.** `/aid-housekeep` checks the Knowledge Base against the code when the project has drifted.

AID adds formal feedback loops to the sequence. You set the direction, and the agents do the work in between.

AID does not replace sprints, backlogs or retrospectives, which can sit alongside AID phases. What AID adds is understanding and specification before implementation.

### The Iron Man Model: Human-in-the-Middle

<ReviewLoop />

*The loop inside Specify, Plan and Detail: the AI proposes, you and the AI discuss, the AI writes, and a reviewer grades. The loop repeats until the grade meets the project's minimum. You approve before the next phase starts.*

You and the AI work together in every phase. The AI does not just execute while you stamp the result, and you do not do all the thinking while the AI types.

**Between phases, you give the OK to advance.** AID never moves to the next phase by itself. You review what a phase wrote, decide whether it is good enough, and start the next phase. This keeps you in control without slowing the work to human speed.

A shortcut works differently. It runs the shared shortcut engine without a stop between its states, except for a question it may ask at INTAKE or in CAPTURE and the final halt. A mechanical grading step then checks every document before the halt. The shortcut path is a faster, narrower variant for small, well-scoped changes. [The pipeline](/concepts/pipeline/#the-shortcut-path) describes it.

### Three core principles

**1. Knowledge before specification**

AID puts understanding before specification. The Discover phase produces a [Knowledge Base](/reference/glossary/#knowledge-base): documents on architecture, conventions, data models, integrations, tech debt and domain language. You write the spec against that knowledge, not from imagination.

A [greenfield](/reference/glossary/#greenfield) project has no existing system to discover, but understanding still comes before specification. `/aid-describe` writes a first set of design documents from your intent: domain language, intended architecture, conventions, technology stack and, when you make rationale-bearing choices, decisions. This reverses the direction used for existing code. The design documents are the source of truth, they carry `source: forward-authored`, and the code is built to match them. Once code exists, `/aid-housekeep` checks it against the design and reports any divergence for you to resolve. It never overwrites the design automatically.

**2. Specs are living documents**

A spec written before implementation is a hypothesis. A spec revised after implementation is knowledge. AID treats specs as living artifacts that change through defined paths, so each revision leaves a record.

This matters most on existing code. The people who built it may have left, the requirements may have changed, and the patterns may be dated. A spec you write may be partly wrong. The question is whether you revise it formally, with a trail, or informally, with silent workarounds.

**3. Feedback over forward-only**

The pipeline is sequential by default, but a later phase can send a finding back to an earlier one. A phase that finds a gap in the Knowledge Base can trigger a targeted discovery. A task that finds a wrong assumption writes an impediment that routes back to the right phase. The loops are formal because real projects are not linear. See [Feedback loops](/concepts/feedback-loops/) for each one.

### What AID removes

Give a capable coding agent a vague task and a large repository, and failures like these can appear. AID addresses each one through process, not prompt tuning.

| **Failure mode** | What it looks like | How AID addresses it |
|------------------|--------------------|----------------------|
| **Knowledge gaps** | The agent does not understand the existing system and invents how it works. | Discover builds the Knowledge Base before any spec is written. |
| **Hallucination** | The agent states things about the code that are not true. | Knowledge Base documents cite their sources with a durable anchor: a file path plus a heading or a searchable string, never a bare line number. A lint checks the citations. See the [Knowledge Base](/concepts/knowledge-base/) page. |
| **Drift** | The implementation quietly diverges from intent, and the spec goes stale. | Specs are revised through feedback loops, and each revision leaves a record. |
| **Overengineering** | The agent adds abstractions, options and scope nobody asked for. | Tasks are typed and small, with explicit acceptance criteria. The reviewer grades against those criteria and against the [declared review criteria](/reference/glossary/#declared-review-criteria) of the file. |
| **Oversights** | Bugs, missed edge cases and untested paths slip through. | A separate reviewer agent grades the work, and the agent that writes does not grade its own work. The loop repeats until the grade meets the bar. |
| **Context exhaustion** | Loading the whole repository into the context window is slow, costly and lossy. | Agents read an index first, then one Knowledge Base document, then an exact location. See [The Knowledge Base page](/concepts/knowledge-base/). |

### An honest assessment

AID is not a silver bullet. It is a trade-off.

| **Where AID helps most** | **Where AID is heavier** |
|--------------------------|--------------------------|
| Existing projects with accumulated complexity and missing documentation | A new MVP where the risk of knowledge gaps is low and discovery is a real cost |
| Regulated settings where audit trails and traceability are required | Teams that already know the codebase well and would be writing down what they know |
| Long-running projects where losing institutional memory is costly | Work where speed is the only goal and the cost of breakage is accepted |
| Teams new to AI-assisted development that need guardrails against the failures above | |

You do not have to weigh the cost of the full pipeline against the value of each change. Small, well-scoped work goes through a shortcut. Broad or unclear work goes to `/aid-describe`. If you are not sure, `/aid-triage` suggests which. [The pipeline](/concepts/pipeline/#three-ways-in) explains the three ways in.

The full path adds process. Discover, Describe, Define, Specify, Plan and Detail all take time before any code is written. The payoff is code grounded in real understanding, with a spec that does not surprise you mid-implementation. For small work, a shortcut keeps the cost in proportion to the change.
