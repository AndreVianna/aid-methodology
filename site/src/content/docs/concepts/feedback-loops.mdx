This page explains how AID sends a finding back to an earlier phase and what each feedback loop leaves for you to resolve.

The pipeline runs forward from `/aid-discover` to `/aid-execute`, but real work is not linear. An assumption breaks, or a gap shows up in a document you trusted. A [feedback loop](/reference/glossary/#feedback-loop) is the formal way for a later phase to send that finding back to the phase that owns it, instead of working around it.

The drawing and its table list every loop: which phase sends the work back, where it goes, and what triggers it. The sections below explain how the loops work. Deploy and Monitor are optional, so their loops apply only when you run those skills.

## Loops leave a record

A loop does not change anything silently. It leaves a record you can read, so you can see what was found and who has to act. The three main records are:

- **A Q&A entry** in a state file. This is the usual record.
- **An `IMPEDIMENT-task-NNN.md` file**, written only by `/aid-execute`.
- **A Monitor finding**, which `/aid-monitor` shows you before it routes anything.

## Q&A entries

A phase that finds a gap in an earlier artifact records a [Q&A entry](/reference/glossary/#qa-entry) in the state file of the area that owns the question:

- A gap in the [Knowledge Base](/reference/glossary/#knowledge-base) goes to `.aid/knowledge/STATE.md`, under `## Q&A (Pending)`.
- A gap in the requirements or a feature goes to the `qa` list in the work's `STATE.yml`.
- When the delivery gate finds a problem in a specification, it records the entry in the delivery's own `STATE.yml`.

The owning phase finds the pending entry the next time you run it and resolves it with you. `/aid-discover` goes to its question state while any entry is pending, and `/aid-describe` does the same for entries in the work's state file. For a Knowledge Base gap, `/aid-discover` re-runs only the agent that owns the affected document, so it never starts a full discovery again.

An entry records the gap, how much it matters, and why the calling phase raised it:

```markdown
### Q{N}

- **Category:** {category, for example Architecture, Requirements or Security}
- **Impact:** {High|Medium|Low|Required}
- **Status:** Pending
- **Context:** {why this matters, what was found, and which phase raised it}
- **Suggested:** {an answer if one can be inferred, or a dash}
```

## Impediments

`/aid-execute` uses a file instead of a Q&A entry when a task meets a contradiction it cannot resolve inside its scope. It marks the task `Failed` and writes `IMPEDIMENT-task-NNN.md` into the work folder. The file holds the type, a description, the options and a recommendation. You decide which option to take.

The type tells you where the work goes next:

| Type | What it means | What happens |
|------|---------------|--------------|
| `kb-gap` | The Knowledge Base is wrong or missing something the agent relied on. | A targeted `/aid-discover` updates it, then the task retries. |
| `architecture-conflict` | The task would break the existing architecture. | You go back to `/aid-specify` for the feature. |
| `missing-dependency` | A dependency the task needs does not exist yet. | You go back to `/aid-detail`, which may add another task first. |
| `wrong-assumption` | An assumption in the task or spec does not hold in the code. | You update the task or the spec, then the task retries. |

After the cause is fixed, the impediment file is deleted and the task starts again. The template is [`IMPEDIMENT.md` in the template folder](https://github.com/AndreVianna/aid-methodology/blob/master/canonical/aid/templates/feedback-artifacts/IMPEDIMENT.md), and the [Artifacts reference](/reference/artifacts/) shows where it sits among the other work files.

## Review findings in Execute

After all the tasks of a delivery are done, a reviewer in a clean context grades the delivery. It tags each issue with where it comes from: `CODE`, `TASK`, `SPEC` or `KB`.

- A `CODE` issue is fixed automatically by the executor agent, and the reviewer checks again.
- A `TASK` issue is shown to you with a suggestion. You update the task.
- A `SPEC` issue is recorded as a Q&A entry, and `/aid-specify` is suggested.
- A `KB` issue is recorded as a Q&A entry, and `/aid-discover` is suggested.

If only issues from the last three kinds remain, the gate stops and tells you what must change upstream, because the problem is not in the code. See [Execute and review](/concepts/pipeline/#execute-and-review) for the rest of the review loop.

## Verification in Deploy

`/aid-deploy` runs a full build, the full test suite and the lint check before it packages a delivery. If something fails, it asks whether you want to fix a minor problem on the spot or go back to `/aid-execute` for a larger one. After three fix attempts in Deploy you must go back to `/aid-execute`.

## Routing from Monitor

`/aid-monitor` classifies each finding as a bug, a change request, an infrastructure issue or no action. It shows you the proposed route and acts only on the routes you approve.

- A bug goes to `/aid-fix`. The specification is already right and only the code is wrong, so the fix skips Specify, Plan and Detail.
- A change request goes to `/aid-triage`, which suggests the right entry: a shortcut for a known single change, or `/aid-describe` for anything broad or ambiguous.
- Infrastructure problems are outside AID. You handle them yourself.

## Keeping the history of a change

The requirements template and the Knowledge Base documents carry no change-log section. Git already records every edit with its author, date and diff, and a hand-kept table drifts from the file it describes. To see why a document changed, ask git:

```bash
git log --follow -p .aid/works/work-001-example/REQUIREMENTS.md
```

To find which revision introduced a claim, search by its text:

```bash
git log -S'the contradicting claim'
```

What git cannot tell you, such as where a work stands in the pipeline, lives in the area's state file.
