This page explains how work moves through AID, from setup to a reviewed task, and which of the three ways in fits your change.

## The order of the phases

<Pipeline />

You run `/aid-config` once to set AID up. Then the numbered phases run in this order: Discover, Describe, Define, Specify, Plan, Detail and Execute. The sequence ends at Execute.

Each phase is a skill. A skill stops when it finishes, you read what it wrote, and you start the next one. AID never moves to the next phase by itself. This stop between phases is the [phase gate](/reference/glossary/#phase-gate).

Two steps sit outside the sequence. `/aid-deploy` and `/aid-monitor` are optional and you invoke each one on its own. `/aid-housekeep` runs on demand when the project has drifted from its [Knowledge Base](/reference/glossary/#knowledge-base).

For the exact steps of each phase, see [Working the pipeline](/guides/pipeline/). For what each skill accepts and writes, see its page in the [Skills](/skills/) section.

## Three ways in

You do not have to weigh the cost of the full pipeline against the size of your change. You choose one of three ways in, and each fits a different kind of work.

- **A shortcut** fits a change whose kind you already know, such as `/aid-fix` or `/aid-create api`. A shortcut runs the [shortcut engine](/reference/glossary/#shortcut-engine), which writes the requirements, specification and tasks in one run.
- **`/aid-triage`** fits the case where you are not sure. You describe the work in a sentence and it suggests the next command. It writes nothing and runs nothing, so you type the command it suggests. If your input is a question rather than a change, it points you to `/aid-ask`.
- **`/aid-describe`** starts the full path. Use it for broad work, work that touches many areas, or a new project.

`/aid-ask` is not a way in. It answers a question about the project, with citations. It is read-only, except that it can record a gap it finds in the Knowledge Base.

The [shortcuts page](/get-started/lite-path/) explains how to choose and run a shortcut. The [Skills](/skills/) index lists the skills, shortcuts included.

## The full path

The full path has one skill per phase. Existing code starts at `/aid-discover`. A project with no code yet starts at `/aid-describe`.

**Discover** builds the Knowledge Base from the code you already have. It runs as a sequence of states, one per invocation: ELICIT, GENERATE, REVIEW, Q-AND-A, FIX and APPROVAL. It writes the documents to `.aid/knowledge/` and records its open questions and review history in `.aid/knowledge/STATE.md`.

**Describe** interviews you about what to build and writes `REQUIREMENTS.md` in a new work folder under `.aid/works/`. On a [greenfield](/reference/glossary/#greenfield) project, with no Knowledge Base yet, it also writes a first set of design documents from your intent. Those documents carry `source: forward-authored`, and the code is then built to match them.

**Define** splits the approved requirements into features. A feature is a `### Feature NNN` section inside `REQUIREMENTS.md`, not a file of its own.

**Specify** takes one feature at a time and writes its technical specification into that feature's section. You name the feature when you run it, for example `/aid-specify work-001/feature-001`.

**Plan** groups the specified features into deliveries and writes `PLAN.md`, with one `### delivery-NNN` section per delivery. It also creates a `STATE.yml` for each delivery.

**Detail** breaks each delivery into small tasks. Each task is a `DETAIL.md` file under `deliveries/delivery-NNN/tasks/task-NNN/`, and the execution graph is added to `PLAN.md`. Every task has one of eight types: RESEARCH, DESIGN, IMPLEMENT, TEST, DOCUMENT, MIGRATE, REFACTOR or CONFIGURE. The type decides how the task is done and how it is reviewed.

**Execute** carries out one task and reviews it. See [Execute and review](#execute-and-review).

Specify, Plan and Detail each work the same way. The agent proposes, you discuss, the agent writes, and a reviewer grades the result. The loop repeats until the grade meets your project's minimum. The [methodology page](/concepts/methodology/#the-iron-man-model-human-in-the-middle) shows this loop. Describe and Define use an interview and a decomposition step instead, and Discover uses the state sequence above.

Every grading phase uses the same rubric. The reviewer lists each issue with a severity, and the [grade](/reference/glossary/#grading) follows from those severities by rule. The reviewer never picks a grade by hand. The minimum grade is the `minimum_grade` setting, which is `A` by default. See [Settings keys](/reference/settings/).

### The work folder

A full-path work has this layout. Each work has its own requirements and shares the Knowledge Base with the others.

```
.aid/
  knowledge/                    shared Knowledge Base
  works/
    work-001-user-auth/
      STATE.yml                 work state: sections, Q&A, grade
      REQUIREMENTS.md           requirements; section 11 holds one
                                "### Feature NNN" section per feature
      PLAN.md                   deliveries and the execution graph
      deliveries/
        delivery-001/
          STATE.yml             delivery state
          tasks/
            task-001/
              DETAIL.md         task definition (from Detail)
              STATE.yml         task state (from Execute)
```

The [Artifacts reference](/reference/artifacts/) describes each of these files.

## The shortcut path

<TwoPaths />

A shortcut skips `/aid-describe` through `/aid-detail`. It runs the shortcut engine, which goes through these states in one run:

```
INTAKE → CAPTURE → SPEC → PLAN → DETAIL → GATE → APPROVAL-HALT
```

The engine collapses the five definition phases into one run. It does not skip them. CAPTURE, SPEC, PLAN and DETAIL run without a stop between them. It can ask you a question at INTAKE (new work or continuation) and, rarely, in CAPTURE, and it stops for your approval at the halt at the end.

GATE grades every generated document. It grades against the `minimum_grade` setting: a per-skill value if the project sets one, otherwise the global value (the shipped default is `A`). APPROVAL-HALT then presents the work and stops. The engine never builds anything. You run `/aid-execute` yourself after you approve.

If works already exist, INTAKE first asks whether this is new work or a continuation. For a continuation it hands you to that work's own command and does not run.

The engine writes a flattened work with one delivery and no `deliveries/` folder:

```
.aid/
  works/
    work-NNN-name/
      STATE.yml             work state, including every task's state
      REQUIREMENTS.md       section 11 holds the single feature and its
                            technical specification
      tasks/
        task-NNN/
          DETAIL.md         task definition
```

Two things differ from the full path. There is no `STATE.yml` per task, because each task's state lives in the work's `STATE.yml` under `tasks_lifecycle`. There is no `PLAN.md`, because one feature in one delivery leaves no order to decide. The execution graph comes from each task's `Depends on` field.

## Execute and review

`/aid-execute` takes one task and works by its type. You name the task, for example `/aid-execute work-001 task-001`. Its states are EXECUTE, REVIEW and DONE for a task, plus a delivery gate that has its own FIX loop.

A separate reviewer agent gives each task a quick check: a CRITICAL finding is fixed on the spot, once, and a HIGH finding is deferred to the gate. When a delivery's tasks are done, a delivery-gate review grades the whole delivery and loops with fixes until the grade meets the minimum. If the grade does not improve for three cycles in a row, the loop stops and shows you your options.

All tasks in a delivery share one branch, named `aid/<work>-delivery-NNN`. When you run Execute on a whole delivery, it runs several independent tasks at once. The limit is the `execution.max_parallel_tasks` setting, which is 5 when the setting is absent.

When the agent finds that an assumption does not hold, it writes an `IMPEDIMENT-task-NNN.md` file instead of working around the problem. The impediment has a type: `wrong-assumption`, `missing-dependency`, `architecture-conflict` or `kb-gap`. It also lists options and a recommendation, and you decide.

Execute records the result in the task's own `STATE.yml`: the task's state and its review history. On the full path that file is `deliveries/delivery-NNN/tasks/task-NNN/STATE.yml`. The delivery's `STATE.yml` moves from Executing to Gated to Done, or to Blocked. On a shortcut work, both live in the work's `STATE.yml`.

## After Execute

`/aid-deploy` and `/aid-monitor` are optional. The numbered pipeline ends at Execute, and neither skill is a step that follows it. A project can ship another way, or skip both.

- `/aid-deploy` packages completed deliveries into a release. It verifies the build, writes a `package-NNN-<name>.md` record and marks the deliveries `Shipped`.
- `/aid-monitor` watches production, classifies what it finds and routes it. It sends bugs to `/aid-fix` and change requests to `/aid-triage`. A bug is code that does not do what the specification says. A change request is a case where the specification itself is wrong for what you now need, or needs a requirements decision.

Both skills also accept a free-form description instead of a work id. In that form they run as shortcuts.

## Keeping the Knowledge Base current

As a project changes, its code drifts away from the Knowledge Base. `/aid-housekeep` closes that gap without a full discovery. It works on its own `aid/housekeep-*` branch, with one commit per stage, through these stages: PREFLIGHT, KB-DELTA, SUMMARY-DELTA, CLEANUP and DONE. If a run stalls, running it again resumes at the stalled stage. `--cleanup-only` jumps straight to CLEANUP.

Design documents marked `source: forward-authored` are handled differently. Housekeep checks whether the code has diverged from them and reports the difference for you to resolve. It never overwrites the design with what the code does.
