**Scope:**
- Create `site/scripts/skills/render-page.mjs`: assemble one detail page in feature-001's fixed order -- page frontmatter (`title`, `description`, `generatedFrom`), the generated marker, the `## Frontmatter` bullet list, the `[Definition: ...]` source link, then the body slot. Page frontmatter is serialized in the siblings' single-quoted style with `'` -> `''`, re-implemented here rather than imported from `gen-reference.mjs`.
- Page `title` is the directory name. Page `description` comes from `skillSummary` imported from `site/scripts/skills/summary.mjs` (task-007) -- **not a private copy of the rule** -- so a card's text and its target page's `<meta name="description">` are the same string. The `[Definition: ...]` link uses `GITHUB_BLOB_BASE` from `paths.mjs`.
- **No `sidebar:` key is emitted.** feature-002 formally released that reserved slot: detail pages sort alphabetically in the autogenerated sidebar tree for free.
- Create `site/scripts/skills/body.mjs`: `BODY_PROVIDERS` and `BODY_APPENDERS` as **empty static array literals**, plus `renderSkillBody(skill)` returning the first matching provider's output followed by every appender's, or `''`. No directory globbing, no dynamic `import()`, no registration side effect -- filesystem enumeration order is not guaranteed and would put AC-6 at the mercy of the OS.
- Providers own their own headings; `render-page.mjs` imposes none, so features 003 and 004 are not boxed into a structure chosen before their charts existed.
- Same conventions as the rest of the cluster: ESM `.mjs`, `node:` builtins only, 2-space indentation, pure exported functions with no import-time side effect, no new dependency.
