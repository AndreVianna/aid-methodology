## Smallest conditional integration

1. Keep scripts under `canonical/aid/scripts/hooks/aid-*`, installed through the existing shared runtime. Add a Codex-specific event/response adapter only for native events whose payload, denial/continuation and error behavior the probes demonstrate. Reuse pure text helpers where appropriate; do not feed Codex records into the Claude parser or claim a model-facing message was withheld from a Stop continuation alone.
2. Extend profile schema and renderer with an explicit, closed Codex hook variant, native settings path and proven event list. Extend descriptor validation/serialization and the Bash/PowerShell host-hook lifecycle branches together; preserve the existing Claude branch. Never expose arbitrary descriptor paths or raw user configuration injection as a shortcut.
3. Retain per-handler ownership via the namespaced script command, manifest event/name/settings/created records, idempotent add/update, removal of only AID handlers, preservation of other groups/keys, and conservative refusal of unsafe/unparseable/symlink settings. Update marker fallback for the actual native settings file; the existing `<root>/settings.json` fallback is insufficient for another filename. Do not delete an existing user file merely because AID removed its last handler.
4. Implement only proven checks. A pre-tool missing-folder denial must prevent the writer call without creating the folder, rewriting arguments or retrying. Failed-write continuation requires reliable result/call identity and turn boundaries. Record/display matching requires actual successful writes or actual-record readback plus question/recommendation/state evidence; an attempted ask or final diff alone is insufficient. Unknown payloads and unobservable tool paths must remain explicit unsupported boundaries, not fabricated enforcement.

## Isolation and version boundaries

- KB `authoring-conventions.md` G-10/G-13 and Content Isolation allow a host-settings handler only when its command names `.aid/runtime/scripts/hooks/aid-*`, the manifest owns it, and uninstall removes it. They do not authorize unrelated feature flags, project trust entries, account configuration or arbitrary content at `.codex/` root. If native loading requires an extra enablement/trust key, report that concrete contract issue before broadening installation. Probe success under trusted private configuration does not authorize changing user trust.
- Do not infer complete hook support, message withdrawal, all-tool coverage, Windows behavior or a minimum supported Codex version from one Linux 0.164.0 run. Record exact observed platform/version and unsupported/error behavior. The profile has no existing minimum-version enforcement mechanism in the inspected hook path.
- Proposed affected tests are existing host-hook lifecycle/descriptor tests and hook-specific offline fixtures: user-key preservation, idempotent update, refusal, exact removal, manifest ownership, Bash/PowerShell parity, known/unknown payloads and result correlation. These were inspected, not executed. No need to alter sample expectations, judges, normalized original events or default model settings.

The existing owner proposal is `.aid/works/work-003-full-aid-restructure/analysis/delivery-003-codex-guard-proposal.md`. Its prohibition on hidden repairs/retries and requirement for actual host proof remain applicable. No integration is approved by this source map alone.
