# Direct-Entry Shortcut Engine

The single shared engine every thin shortcut doorway (`.agents/skills/aid-<name>/
SKILL.md`) delegates to. Implements the state machine **INTAKE -> CAPTURE -> SPEC ->
PLAN -> DETAIL** -- the definition work (the Describe, Define, Specify, Plan and Detail
steps) collapsed into one fast, mostly-autonomous run. It produces
the **full** flattened artifact set (feature-001 shape); it never skips a phase, it
collapses the information capture within each phase. It never builds -- Building is a
separate, user-initiated `/aid-execute`.

> **Maintenance note:** the states in order are INTAKE -> CAPTURE -> SPEC -> PLAN ->
> DETAIL -> GATE -> APPROVAL-HALT. GATE and APPROVAL-HALT (feature-004) were authored by
> task-011 below the `<!-- GATE / APPROVAL-HALT insertion point -->` marker near the end of
> this file. Do not insert new states between INTAKE and DETAIL above the marker; GATE and
> APPROVAL-HALT are the terminal two states and nothing follows them.

## Invocation Contract

A thin doorway's body (see `.agents/skills/aid-<name>/SKILL.md`, generated by
`build-shortcut-skills.py` from the row's `{verb, artifact}`) hands this engine four
bound values, and a fifth when `/aid-orchestrate` hands the reading over, before the
state machine below starts:

| Value | Source | Notes |
|---|---|---|
| `{name}` | the invoking doorway's own directory/skill name (e.g. `aid-create-api`) | used for the catalog lookup and the `STATE.yml` Active Skill field |
| `{verb}` | the doorway body's binding | dispatch key; drives the family scaffolding lookup |
| `{artifact}` | the doorway body's binding (may be `""` for a bare verb) | narrows the family scaffolding lookup |
| `{description}` | the user's free-text argument (`argument-hint`) | may be absent/empty -- see CAPTURE Step 1 |
| `{intent}` | the hand-over's `intent:` line followed by its indented keys (`request`, `reading`, `reason`, `depth`, `phases`, `changes`) | absent for a typed `/aid-<skill>`; set on the record by INTAKE Steps 4 and 5 |

## Design Notes

- **Autonomous, non-interactive authoring.** Unlike the full path's per-phase
  Propose/Discuss/Write/Review loops (`aid-plan`, `aid-detail`), CAPTURE/SPEC/PLAN/DETAIL
  run without a per-state user checkpoint -- the whole point of the engine is fewer
  turns (NFR-5). The only inline user-facing moments are (a) CAPTURE's single
  load-bearing-gap question (rare; see Capture-Minimization Rules), and (b) the terminal
  APPROVAL-HALT presentation (added by task-011/feature-004). Quality is enforced once,
  mechanically, by the GATE state's grading loop -- not by a human checkpoint at every
  state.
- **One run, one work -- gated at the front door.** INTAKE consults the shared Work
  Initiation Gate (`.aid/runtime/templates/work-initiation-gate.md`) *before* it
  allocates (INTAKE Step 3): when no works exist it proceeds and allocates a brand-new
  `work-NNN`; when works already exist it asks the user new-vs-continuation. On
  "continuation", follow the gate's § 3b: enter the chosen work's worktree and run the skill
  its record names, at its saved step. So the engine still only ever **authors one fresh
  work per run** (it carries no `work-NNN` resume argument -- contrast `aid-plan`/`aid-detail`,
  which accept one); the gate supersedes the old "always allocate a brand-new work" rule with
  an explicit gate. The common-case NEW run drives INTAKE all the way to the terminal
  halt in one continuous invocation
  (`.aid/runtime/templates/skill-steps.md` CHAIN), pausing only for the
  gate's question (when works exist), CAPTURE's rare inline question, and the terminal
  halt.
- **Resuming a halted run (the engine is not re-entered).** Each state saves its own step
  with the writer before it works (see the state-entry paragraph under State Machine), so a
  session that stops mid-run has its place in the record. Continuing a work is the Work
  Initiation Gate's job: on "continuation" it runs the skill the record names, at its saved
  step (gate § 3b), and a halted Lite work resumes at APPROVAL-HALT, which asks the
  approval while it is still open (and, once it was given, only tells the user to run `/aid-execute`). Re-running the shortcut never re-enters this engine's states.
- **Forward-compatible with incremental family landings.** Family features 005-013
  land `shortcut-scaffolding/<family>.md` references incrementally. Every state below
  degrades gracefully to the generic minimal-capture / single-task default when a
  family's scaffolding file does not exist yet (see Family Scaffolding Consult) -- the
  engine is fully functional the moment any catalog row exists, even before its
  family's reference file lands.

## Dispatch Protocol

Every `aid-architect` dispatch in CAPTURE/SPEC/PLAN/DETAIL follows the standard
checklist at `.aid/runtime/templates/dispatch-protocol-checklist.md` (ETA lookup,
heartbeat file, 3 L2 timers, `[?] done` / `[x] FAILED` bracket pairs -- see that file
for the exact `▶`/`✓`/`✗` presentation). Look up the ETA band for `aid-architect` in
`.aid/runtime/templates/rough-time-hints.md`. On completion, emit the closing `✓ ...
done in <actual>` bracket (the checklist's own completion step) -- this narration is
the only persisted record of a CAPTURE/SPEC/PLAN/DETAIL dispatch: the work-level
Calibration Log / Dispatches views are now DERIVED at read time solely from per-task
`dispatch_log` entries (`work-state-template.yml`), which do not exist until
`/aid-execute` dispatches an actual `task-NNN`; there is no work-root key left for a
document-level (non-task) dispatch to append to, unlike the retired `## Calibration
Log` markdown section which any dispatch -- task-scoped or not -- could append a row
to directly.

## State Machine

| State | Detail | Worker | Advance |
|---|---|---|---|
| INTAKE | below | inline | CHAIN → CAPTURE |
| CAPTURE | below | `aid-architect` (Large) | CHAIN → SPEC |
| SPEC | below | `aid-architect` (Large) | CHAIN → PLAN |
| PLAN | below | `aid-architect` (Large) | CHAIN → DETAIL |
| DETAIL | below | `aid-architect` (Large) | CHAIN → GATE |
| GATE | below | `aid-reviewer` (Large) | CHAIN → APPROVAL-HALT when both passes clear; CHAIN → GATE when a pass is below the floor and the circuit breaker has not tripped; HALT when the circuit breaker has blocked the work |
| APPROVAL-HALT | below | inline | CHAIN → CAPTURE when the requirements must change; CHAIN → DETAIL when only the task set must change; HALT when approved or dropped |

On entry to each state, before its work, the state saves its own step: `bash .aid/runtime/scripts/execute/writeback-state.sh --step
--skill {name} --name <STATE>` (`.aid/runtime/templates/skill-steps.md`, the step procedure).
INTAKE is the exception: the work does not exist until its Step 4 creates it, with
`--step INTAKE`. Route each completed state's `**Advance:**` per
`.aid/runtime/templates/skill-steps.md`. Every transition below is a CHAIN except APPROVAL-HALT,
which asks the approval, reads the answer, and then either loops back or halts. A question that
comes up in INTAKE or CAPTURE pauses that state where it stands, and the state goes on once it is answered (skill-steps.md,
"Questions, at any point").

Talking with the user: follow `.aid/runtime/templates/question-protocol.md`.

**Agent dispatch (C-2).** Authoring states (CAPTURE/SPEC/PLAN/DETAIL) dispatch
`aid-architect` (Large tier -- design work, mirroring how `aid-describe`'s former
lite-path task-breakdown step used `aid-architect` before that lite path was retired);
GATE dispatches `aid-reviewer` (Large -- matches the Large `aid-architect` executor,
preserving reviewer tier >= executor tier). The writer never grades its own work
(`architecture.md § Agent / Sub-Agent Dispatch Model`). **Effort** (not tier) is the
cost lever here per `.aid/runtime/templates/agent-dispatch-tiering.md`: dispatch
`aid-architect` at `medium` effort by default (escalate to `xhigh` only for a genuinely
hard decomposition -- a large multi-feature SPEC or a non-trivial task graph), and the
GATE `aid-reviewer` scales its effort to the artifact (`medium` for a small/simple
change, `high` for a complex/security/design one). Do not leave effort at the host
default (`high`) for routine changes.

## Capture-Minimization Rules

Generic slot inventory (used whenever no family scaffolding file overrides it), mapped
onto `REQUIREMENTS.md`'s 10 sections. Every slot below is answered from
`{verb, artifact, description}` + KB context wherever possible; only a genuinely
load-bearing gap escalates to CAPTURE's single inline question (CAPTURE Step 3).

| REQUIREMENTS.md section | Default source | Escalates only when |
|---|---|---|
| §1 Objective / §2 Problem Statement | `{description}` (verbatim or lightly restated) | `{description}` is empty (INTAKE Step 2's bootstrapping question) |
| §3 Users & Stakeholders | Inferred (typically "the requesting developer/maintainer"; a KB module owner if named) | description names a distinct external user group not inferable from context |
| §4 Scope | `{verb, artifact}` + `{description}` bound the scope by construction | description leaves the "in scope" boundary genuinely ambiguous (e.g. touches multiple unrelated artifacts) |
| §5 Functional Requirements | `{description}` + family scaffolding guidance | **load-bearing** -- cannot be stated concretely without more information |
| §6 Non-Functional Requirements | `N/A` for a small shortcut-scoped change unless `{description}` names a target (perf, security, etc.) | never escalates -- mark `N/A` or `*(pending)*`, do not ask |
| §7 Constraints | `N/A` unless `{description}`/KB names one | never escalates |
| §8 Assumptions & Dependencies | KB context (`.aid/knowledge/INDEX.md`) | never escalates -- best-effort from KB; `*(pending)*` if none found |
| §9 Acceptance Criteria | Derived from §5 + the family scaffolding's task-breakdown shape | **load-bearing** -- cannot be stated as testable Given/When/Then without more information |
| §10 Priority | `Must` (default -- the user invoked the shortcut) | never escalates |

**The escalation rule:** ask a question only when §5 or §9 cannot be made concrete and
testable from everything already known. One question per genuine gap, each on its own topic and asked
one per message (question-protocol.md Rule 1), most important first (§5 before §9);
never fold two gaps into one question -- this is
the same minimal-slot discipline the retired `aid-describe` lite-path slot-fill step once
used (D-2): it drew out only the route-deciding signals; CAPTURE here draws out only the
SPEC-deciding ones, because the route (`{verb, artifact}`) is already fixed by the invocation.

## Default-Type Mapping (A-6)

Code-settled; no enum change (extending the 8-type enum is a lockstep break across
`grade.sh`, both dashboard reader twins, and every grading skill --
`artifact-schemas.md § Contracts`). The authoritative value for any given shortcut is
always its own catalog row's `default_type` field, not a re-derivation from this table:

| Verb (representative) | Default task Type | Note |
|---|---|---|
| create / update (code, api, ui, cli, messaging, integration, infra) | IMPLEMENT | |
| create-data-model / update-data-model | MIGRATE (+ IMPLEMENT) | entity/schema + migration |
| create-config / update-config | CONFIGURE | feature-flag / rule |
| fix | IMPLEMENT | |
| refactor | REFACTOR | |
| create-test / update-test (test authoring) | TEST | each test traces to an acceptance criterion |
| experiment | RESEARCH | hypothesis -> analyze -> recommend |
| create-dashboard / update-dashboard (BI view) | IMPLEMENT | source -> visualization -> publish/refresh; a durable BI view is code/config |
| remove | REFACTOR | delete without changing surviving behavior; dependents/tests/docs updated (structural, not a defect fix) |
| deprecate | IMPLEMENT | add a warning + migration path; artifact still functions |
| migrate | MIGRATE | data/dependency/framework/platform move + rollback plan (non-schema; schema migrations stay create/update-data-model) |

Multi-task shortcuts (e.g. create-data-model -> MIGRATE + IMPLEMENT + TEST) emit
several tasks at DETAIL, each with one Type (never mixed --
`artifact-schemas.md § Task DETAIL.md`).

## Family Scaffolding Consult

CAPTURE, SPEC, and DETAIL each consult the per-family reference whose path is given in
the **Current verb → family-file groupings** table below -- that table is **the
authoritative verb-to-file mapping for this engine**. A family that groups more than
one verb under one file documents that grouping in its own file header (the table
collects them at a glance). A verb absent from the table falls back to the generic
rules stated in this file (see Absent-file fallback).

**Current verb → family-file groupings** (authoritative verb-to-file mapping; kept
current as each family lands; a family that groups more than one verb documents
the grouping in its own file header, the same incremental-growth precedent
`Default-Type Mapping (A-6)` above already follows):

| Verb(s) | Family file |
|---|---|
| `create` | `shortcut-scaffolding/create.md` |
| `update`, `refactor` | `shortcut-scaffolding/change-refactor.md` |
| `fix` | `shortcut-scaffolding/fix.md` |
| `experiment` | `shortcut-scaffolding/test-experiment.md` (test AUTHORING -> create.md/change-refactor.md `test` artifact; test RUNNING -> hand-authored aid-test + kind-siblings, work-005) |
| `remove`, `deprecate`, `migrate` | `shortcut-scaffolding/change-refactor.md` |

`query` (the `aid-ask` `repurpose: true` row) is deliberately absent from this table
-- that row never enters this engine at all (its doorway is the hand-authored,
single-shot `.agents/skills/aid-ask/SKILL.md`, not a generated thin doorway over
INTAKE-DETAIL).
The `design` family is deliberately absent for the same reason: like `query` it is not a
generated engine verb, and its omission here is intentional, not an oversight -- do not
"fix" the gap by minting a row for `design` as that family grows from one artifact toward
CC-7's full set.

These reference files are free-form prose (like any other `state-*.md` reference doc)
-- the dispatched `aid-architect` reads them for judgment; they are not
machine-parsed. Each documents, for its verb x every artifact it takes (or once, for a
bare verb):

- **CAPTURE:** the minimal slot list beyond the generic ones above, and any additional
  escalation triggers specific to that verb x artifact.
- **SPEC:** which conditional `## Technical Specification` sections to activate.
- **DETAIL:** the default task breakdown (count, types, dependencies).

**Absent-file fallback (forward compatibility):** when
`shortcut-scaffolding/{family}.md` does not exist yet (its family feature has not
landed), every state falls back to the generic rules stated in this file (Capture-
Minimization Rules; the mandatory-three-sections-only SPEC shape; DETAIL's single-task
`default_type` fallback). This keeps every catalog row usable the moment it is added,
independent of its family reference's landing order.

## State: INTAKE

Purpose: parse the bound invocation values; resolve the catalog row; consult the Work
Initiation Gate (new-vs-continuation) and, on NEW, allocate a new `work-NNN`; scaffold
`STATE.yml` (its top-level frontmatter-zone keys only). FR-2. Size never skips a step of the
workflow: the STATE.yml, the documents and the gates run for a one-line change too.

### Step 1: Resolve the catalog row

Read `.aid/runtime/templates/shortcut-catalog.yml`. Find the row whose `name` equals
`{name}`. Record `default_type`, `group`, `intent`, `alias_of` from that row.

- **Row not found** (a shipped doorway with no matching catalog row -- a build/catalog
  drift, not a user error): STOP. Tell the user, in one plain line, that no
  shortcut-catalog.yml row exists for '{name}', that this is a build defect and not a usage
  error, and that it must be reported. Do not guess a `default_type`.

### Step 2: Resolve the description

If `{description}` is present and non-empty, keep it as-is. If it is empty (the user
invoked the shortcut with no argument), ask the single bootstrapping question now, under
`.aid/runtime/templates/question-protocol.md`, before anything is allocated:

```
Work -- question 1 of 1 -- importance: High
What do you want to {verb}{ optional artifact suffix, e.g. " (api)" when artifact != ""}?
Briefly describe it -- one or two sentences is enough.
Why I ask: the work record keeps your own words as its request, and nothing can be planned without them.
My recommendation: describe it in one or two sentences; a free answer is fine.
Or answer in your own words, ask me to explain, or skip this question.
```

No work exists yet, so this question is recorded in a design document, as the gate's "Recording the
questions asked before a work exists" says (`.aid/runtime/templates/work-initiation-gate.md`): before it is
shown, `bash .aid/runtime/scripts/execute/writeback-state.sh --ask --design
.aid/design/untitled-<YYYYMMDD-HHMMSS>.md --category Scope --impact High --context '<the question, as
shown>' --suggested '<your recommendation>' --asked-by {name}`, and after the reply `--answer --design` on the
same file with `--id` set to the id the writer printed. Once the description gives the work its slug, move the
document with `bash .aid/runtime/scripts/execute/writeback-state.sh --rename-design
.aid/design/untitled-<YYYYMMDD-HHMMSS>.md --to .aid/design/<slug>.md`, and keep that file as this run's seed.

The answer becomes `{description}`. The work record's request is the user's own words and the
writer refuses an empty one, so when the user does not answer, nothing is allocated.

### Step 3: Consult the Work Initiation Gate, then allocate work-NNN

**First, consult the shared Work Initiation Gate**
(`.aid/runtime/templates/work-initiation-gate.md`) before allocating anything. Run its
enumeration helper:

```bash
bash .aid/runtime/scripts/works/enumerate-works.sh
```

- **No works exist anywhere (empty output)** -> proceed with the allocation below, no
  prompt (the common first-work case).
- **One or more works exist** -> ask the gate's single new-vs-continuation question,
  showing the enumerated list (main tree + every git worktree), recorded in the design document like
  Step 2's question (the gate's "Recording the questions asked before a work exists"). On **new work**, proceed with
  the allocation below. On **continuation**, follow the gate's § 3b: enter the chosen work's
  worktree and run the skill its record names, at its saved step. This engine allocates
  nothing and this run ends there.

**Resolve `<work-id>` (only on the NEW branch).** The new work is `work-{NNN+1}`, where
`NNN` is the **maximum `work-NNN` numeric prefix across every record the enumeration above
already returned** (cross-worktree by construction); parse each record's column-1 full
folder id for its leading `work-([0-9]+)` and take the maximum -- `work-001` if the
enumeration returned no records at all (the same allocation rule `aid-describe` uses; see
its `SKILL.md § Task Routing`). **Never** re-scan a local `.aid/works/` glob for this
number: the worktree about to be created is freshly branched off `master`, which tracks no
`.aid/works/` at all, so a fresh local glob inside it would find nothing and re-allocate a
colliding `work-001` (`work-initiation-gate.md § 3a`, "Next-work-NNN derivation").
Derive a short kebab-case slug from `{description}` (first few salient words, kebab-cased,
the same style as any other AID work-folder name). The slug is a cosmetic identifier only;
it is never renamed after the fact.

**Create and enter the worktree, BEFORE authoring anything:**

```bash
bash .aid/runtime/scripts/works/worktree-lifecycle.sh create <work-id> <name>
```

Idempotent (a no-op re-print if the worktree already exists, keyed on the `<work-id>`
branch); prints the worktree's **absolute path** on success/no-op; exits 0 on
success/no-op, non-zero with **empty stdout** on failure. **Create-failure guard
(fail-closed):** on a non-zero exit **or** an empty path, surface the error and **STOP** --
do **not** fall through to allocate the new work on the current (possibly `master`) tree. On
success, **enter** the resolved path per
`.aid/runtime/templates/worktree-lifecycle.md § Step 2` (host-native `EnterWorktree` tool
where available, else treat the resolved path as the working directory for all subsequent
file operations and surface it to the user -- FR4 fallback).

### Step 4: Scaffold STATE.yml through the gate

Allocate through the gate's § 3a (its steps 3 to 5), inside the entered worktree:

1. **The work's type.** When `{intent}` is bound, it is the `reading` of `{intent}`. Otherwise
   read it from the user's words with `/aid-orchestrate`'s `references/check-intent.md`. The
   catalog row's `default_type` names a task type, not a reading, and is not used here.
2. **The folder.** Create `.aid/works/<work-id>-<slug>/`, reusing the `<work-id>` resolved in
   Step 3 (do **not** re-derive it from the fresh worktree's own, still-empty `.aid/works/`).
3. **The record.** Resolve this shortcut's own minimum grade, then make the work record in one
   locked write:

```bash
bash .aid/runtime/scripts/config/read-setting.sh --skill {name} --key minimum_grade --default A+
bash .aid/runtime/scripts/execute/writeback-state.sh --create \
  --work-dir .aid/works/<work-id>-<slug> \
  --reading <type> --request '{description}' \
  --skill {name} --step INTAKE --phase Definition \
  --path lite --minimum-grade <resolved value> \
  [--seed .aid/design/<seed>.md]
```

Pass `--seed` whenever a design document matches: `.aid/design/{artifact}.md` when it exists and
`{artifact}` is non-empty (the seed Step 2 of CAPTURE reads), else the document that recorded this run's
questions (Step 2's or Step 3's). The writer adds it to the work's `sources:` and copies its `## Questions`
rows into the work's `qa` list; the document itself is left unchanged. With neither, omit `--seed`.

When `{intent}` gives a `depth`, add `--depth <that depth>` to the command, so the record holds
it; with none recorded, full applies.

`--create` fills the record from `work-state-template.yml` in that one write:
`intent.reading`, `intent.request`, `active_skill` (`{name}`), `step` (`INTAKE`),
`pipeline.initiator` (`{name}`), `phase` (`Definition`), `pipeline.path` (`lite`, always: this
engine only ever produces the flattened, single-delivery, no-`deliveries/`-wrapper shape),
`minimum_grade`, `lifecycle: Running`, `started` and `updated`. It refuses an existing
`STATE.yml` (exit 8). A non-zero exit stops this state at once: tell the user, in one plain
line, what failed, and that nothing more runs until it is fixed.

Every other key keeps its template value. The template's STATE ADVANCEMENT ORDERING `#` comment
block is static and never rewritten; the `interview` key is an `aid-describe`-only structure
and stays at its scaffolded Pending defaults, unused, for shortcut-generated works;
`delivery_lifecycle` / `tasks_lifecycle` / `delivery_gate` keep their template placeholder values
until PLAN/DETAIL fill them for real; the flattened-only `delivery_state`, `gate_tier`,
`gate_grade` and `gate_timestamp` keep their placeholders until PLAN/DETAIL (`delivery_state`)
and the GATE state (`gate_tier`/`gate_grade`/`gate_timestamp`) fill them; and the DERIVED views
that carry no key at all are, by construction, never written by this engine.

### Step 5: Write the hand-over `reason` and `phases` (only when `{intent}` was passed)

When `{intent}` is bound (Invocation Contract), Step 4 has already written its `request`,
`reading` and `depth` on the record, and `--reroute` is the only later way to change them. This
step sets `reason` and `phases` through the writer, in one write:

```bash
bash .aid/runtime/scripts/execute/writeback-state.sh --intent \
  --reason '<reason of {intent}>' --phases <P1,P2,...>
```

`--phases` is the comma-separated phase names of `{intent}` (Preparation, Definition,
Specification, Planning, Building, CI); the writer stores them as a block list. A work whose
`--create` call already carried `--reason` and `--phases` needs no second write. `changes` is
never copied from `{intent}`: only `--reroute` appends to it. When `{intent}` is not bound (a
typed `/aid-<skill>`), write nothing; the rest values stay.

**Idempotency:** this state never re-runs within an invocation -- an invocation that reaches
allocation (the gate's NEW branch, Step 3) allocates exactly one brand-new work (Design Notes);
a CONTINUATION invocation never reaches this state, because the gate's § 3b runs instead. No
idempotency check is needed.

**Advance:** CHAIN → CAPTURE.

## State: CAPTURE

Collapses the Describe work. Authors the work-root `REQUIREMENTS.md` (all 10 numbered
sections, terse but complete) with the minimum information the already-known
`{verb, artifact}` binding leaves genuinely open. FR-1, FR-3, FR-7.

### Step 1: Bootstrapping question (only when `{description}` is empty)

INTAKE Step 2 asks the bootstrapping question before the work record exists, because the
record's request is the user's own answer. CAPTURE asks nothing here: `{description}` is
non-empty by the time this state runs. (The question is the engine's own minimal analogue of
`aid-describe`'s D1 opener -- narrower, because `{verb, artifact}` already answers what
`aid-describe`'s opener has to draw out from scratch.)

### Step 2: Read context

- `.aid/knowledge/INDEX.md`, if present -- KB references the write-up can cite instead
  of re-deriving from scratch (the same convention `state-first-run.md § 1a` uses).
- `.aid/runtime/templates/shortcut-scaffolding/{family}.md`, if it exists (Family
  Scaffolding Consult above). Read it for this shortcut's minimal-slot list and any
  KB-informed skip rules for this `{verb, artifact}`. If the file does not exist yet,
  fall back to the Capture-Minimization Rules above unmodified.
- `.aid/design/{artifact}.md`, read **if it exists and `{artifact}` is non-empty** --
  the design seed for this artifact, loaded as PRIOR CONTEXT for Step 3's slot set. It is
  an input to the write-up, **never a substitute** for it, and is **never edited, moved
  or deleted** by the run. If the file is absent or `{artifact}` is `""`, CAPTURE
  proceeds exactly as before.

### Step 3: Determine the minimal slot set

Apply the Capture-Minimization Rules above (or the family file's own slot list when
Step 2 found one) to decide what is already answerable from
`{verb, artifact, description}` + KB context, and what remains a genuine gap. Escalate
to one more inline question only for a load-bearing gap -- normally this means §5
Functional Requirements or §9 Acceptance Criteria cannot be stated concretely and
testably from what is already known. Ask one question per load-bearing gap, one topic per
message, most important first; never fold two gaps into one question. Ask only the
gaps that are genuinely load-bearing (bounded minimal-slot fill, not a conversational
interview).

### Step 4: Dispatch aid-architect to author REQUIREMENTS.md

Dispatch `aid-architect` (Large; per the Dispatch Protocol above) with: `{name}`,
`{verb}`, `{artifact}`, `{description}`, any Step 1/Step 3 answers, the KB pointer, and
the family scaffolding pointer (or "none landed yet"). The agent writes
`.aid/works/{work}/REQUIREMENTS.md` seeded from
`.aid/runtime/templates/requirements/requirements-template.md`:

- **Identity block** (MUST, the same composition rule `aid-describe`'s former
  lite-path condensed-intake step used before that lite path was retired):
  `**Name:**` a concise Title-Case title (no trailing period; derived from the
  description/verb+artifact, NOT the `work_id` slug); `**Description:**` exactly one
  sentence (no trailing period).
- **All 10 numbered sections**, terse but complete: fill every section the captured

(per-skill override ->

### Step 4: The Generic REVIEW -> GRADE -> FIX loop (shared by both passes)

1. **REVIEW.** Dispatch `aid-reviewer` (Large; follow the Dispatch Protocol
   above -- ETA lookup, heartbeat file, 3 L2 timers) in a **clean context**
   that never inherits the authoring `aid-architect`'s reasoning
   (`architecture.md § Agent / Sub-Agent Dispatch Model`). Hand-craft the
   inline 5-section brief (`ARTIFACTS UNDER REVIEW` / `CONTEXT` / `RUBRIC` /
   `OUT OF SCOPE` / `OUT-OF-SCOPE FINDINGS POLICY`) from this pass's own
   bullets (Step 2 or Step 3), per `reviewer-dispatch.md § One-off reviews`
   -- there is **no** shared `reviewer-brief.md` for the shortcut engine
   (that file exists only per-skill under
   `.agents/skills/<skill>/references/`). On cycle 1 the ledger does not
   exist yet; the reviewer creates it. On cycle N>=2 the reviewer reads the
   existing ledger first, re-verifies every existing `Pending` row against
   disk (-> `Fixed` if resolved, left `Pending` otherwise), re-verifies
   every `Fixed` row (-> `Recurred` if regressed), then appends newly-found
   issues as `Pending` (`reviewer-ledger-schema.md § Lifecycle`).
2. **GRADE.**
   ```bash
   bash .aid/runtime/scripts/grade.sh --explain <ledger-path>
   ```
   Because the operative floor for this work is `A+` (zero findings --
   `grading-rubric.md` Grade Calculation), and a batched ledger's total
   finding count is the sum of every reviewed document's own finding count,
   the pooled grade equals `A+` **if and only if every individual document
   in the pass also has zero findings**. This preserves the required property:
   each document still clears `minimum_grade` via its own REVIEW->FIX loop
   within the pass -- the batched dispatch changes round-trip **granularity** only,
   never the per-document guarantee (AC-11), so no second, per-document
   `grade.sh` pass is needed at the shortcut path's `A+` floor. (A project
   override that lowers `minimum_grade` below `A+` would need the
   ledger's own `Doc` column read per-document before trusting the pooled
   number; that is outside this engine's default scope and is not built
   speculatively.) If the pass's grade `>= {floor}` -> the pass clears;
   advance (Pass 1 clearing -> Step 3; Pass 2 clearing -> Step 5). Otherwise
   -> Fix below.
3. **FIX.** Dispatch `aid-architect` (Large; same Dispatch Protocol; the
   same tier that authored these documents -- reviewer tier `>=` executor
   tier and the writer, never the reviewer, fixes --
   `architecture.md § Agent / Sub-Agent Dispatch Model`) with every
   `Pending`/`Recurred` row from the pass's ledger. The architect addresses
   each row's cited `Doc`/`Line` in place; it does **not** touch the
   ledger's `Status` column -- that is the next REVIEW cycle's job
   (`reviewer-ledger-schema.md § Authoring rules for the fixer`). Then the
   pass is reviewed again by a fresh, clean-context reviewer (Step 1): the
   `CHAIN → GATE` case of this state's **Advance** line, which resumes at the pass
   not yet cleared.

   **Circuit breaker.** If the pass's grade has not improved across 3
   consecutive cycles, STOP (mirrors
   `.agents/skills/aid-execute/references/state-delivery-gate.md § Step
   5`; `quality-gates.md § The Per-Phase REVIEW to FIX Loop`). Write
   `.aid/works/{work}/IMPEDIMENT-gate-{pass}.md` (`{pass}` = `defn` or `tasks`)
   and:
   ```bash
   bash .aid/runtime/scripts/execute/writeback-state.sh --pipeline --field Lifecycle --value Blocked
   bash .aid/runtime/scripts/execute/writeback-state.sh --pipeline --field "Block Reason" --value "GATE {pass} pass circuit breaker -- grade not improving after 3 cycles"
   bash .aid/runtime/scripts/execute/writeback-state.sh --pipeline --field "Block Artifact" --value ".aid/works/{work}/IMPEDIMENT-gate-{pass}.md"
   bash .aid/runtime/scripts/execute/writeback-state.sh --pipeline --field Updated --value "$(date -u +%Y-%m-%dT%H:%M:%SZ)"
   ```
   and surface it to the user instead of looping further; the state ends on the `HALT`
   case of its **Advance** line.

## State: APPROVAL-HALT

Terminal state (FR-10 / NFR-10). Presents the flattened, GATE-cleared work
and **STOPS**: no branch is created, no task executes. Execution is a
separate, user-initiated `/aid-execute` run; the pipeline never
auto-advances past a human gate (`architecture.md § Invariants`). A grade
`>= minimum_grade` is necessary but not sufficient -- the human gate below
is the other half.

### Step 1: Present the flattened work

Print a summary the user can approve or reject:

```
Flattened work ready for approval; nothing has executed.

work-{NNN}-{slug}  (/{name})
  REQUIREMENTS.md
  tasks/
    task-001  {Type}  {Title}
    task-002  {Type}  {Title}
    ...

GATE: Pass 1 (definition docs) {pass-1-grade}  ·  Pass 2 (task set) {pass-2-grade}  ·  floor {floor}

Nothing has executed. Review the documents above.
```

That block is for a technical user. To a user who writes in plain words, the approval message gives a plain
summary instead: what will change, why, and what they get. It keeps ledger paths, grades, file names and
code out unless they asked; a technical choice they cannot judge is recorded `Assumed` and listed in
plain words (`rules.md` § Asking the user).

### Step 2: Record the approval, pause, and ask

On a resume, read the step detail first. If it says the approval is already recorded as `Q<n>`, do
not run `--ask` again: ask that open question first (Step 3). If it says the approval was given,
tell the user to run `/aid-execute {name-or-work-id}` and end the run (**Advance** below, the
approve case).

Otherwise record the approval before it is shown (`.aid/runtime/templates/question-protocol.md`; an
approval cannot be skipped, so it stays open until the user approves or declines). The call prints
the question's id, `Q<n>`:

```bash
bash .aid/runtime/scripts/execute/writeback-state.sh --ask --category Approval --impact High --asked-by {name} --step APPROVAL-HALT --covers "flattened work: requirements and task set" --context "Approve the flattened work so /aid-execute can start?" --suggested "Yes, once you have reviewed the documents above"
```

Then keep the same step saved with the open question in its detail, and pause the pipeline:

```bash
bash .aid/runtime/scripts/execute/writeback-state.sh --step --skill {name} --name APPROVAL-HALT --detail 'done: GATE cleared and approval recorded as Q<n>; waiting for Q<n>'
bash .aid/runtime/scripts/execute/writeback-state.sh --pipeline --field Lifecycle --value Paused-Awaiting-Input
bash .aid/runtime/scripts/execute/writeback-state.sh --pipeline --field "Pause Reason" --value "Waiting for the user: Q<n>"
bash .aid/runtime/scripts/execute/writeback-state.sh --pipeline --field Updated --value "$(date -u +%Y-%m-%dT%H:%M:%SZ)"
```

The top-level `delivery_state` key is already `Specified` (set at DETAIL Step 4); APPROVAL-HALT does
not touch it -- FR-10/AC-3 requires `Specified` at halt.

Then ask the approval, in the question protocol's form.

### Step 3: Read the answer

The answer is read in this conversation, or by the session that resumes later and asks `Q<n>` first.
Record it with `--answer --id Q<n> --state Answered`, with the user's words as `--value`, and set the
lifecycle back to `Running` (`--pipeline --field Lifecycle --value Running`, which also clears the
pause reason). Then branch on the answer:

- **Approved.** Save the detail so a resume does not ask twice:
  `--step --skill {name} --name APPROVAL-HALT --detail 'approved as Q<n>; next: /aid-execute {name-or-work-id}'`.
  The lifecycle stays `Running` so that `/aid-execute` can take the work up (it stops on any other
  value). Tell the user to run `/aid-execute {name-or-work-id}`; this engine never starts it.
- **Declined, with a change to the requirements** (the user wants the work reshaped): CAPTURE runs
  again with the change the user asked for, and the later states follow, so GATE clears both passes
  again before a new approval is asked. CAPTURE saves its own step on entry.
- **Declined, with a change to the task set only**: the same, from DETAIL.
- **Declined, the user drops the work**: set `--pipeline --field Lifecycle --value Canceled`
  (the writer clears the saved skill and step); nothing has executed, so nothing else is undone.

**Advance:** CHAIN → CAPTURE when the requirements must change; CHAIN → DETAIL when only the task set
must change; HALT when the work is approved (the run ends; `/aid-execute` is a separate,
user-initiated run) or the user drops it. No branch is created; no `tasks_lifecycle` entry
advances past `Pending` (the halt-proof fixture in feature-004's testing
strategy asserts both).
