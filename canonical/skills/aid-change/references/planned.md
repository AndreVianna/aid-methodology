# Planned work

Write one short goal card and plan: the user's goal, exclusions, testable criteria, milestones with tasks tied to criteria, and a budget. Capture the user-visible outcomes, applicable KB facts and project rules, and the checks that demonstrate each outcome. For removed or replaced behavior, check which user needs must remain and which the request intentionally changes. Ask an independent reviewer to check the plan against the original request before presenting the card and plan together for approval. Do not build until approved.

Use `.aid/runtime/scripts/change/trace.py --file plan.json` with `criteria` as a list of criterion IDs and `tasks` as objects with unique `id` and a nonempty `criteria` list. Resolve missing, unknown or unlinked items before building.

Ask a different agent to write acceptance tests; wait for it. Include positive checks that would reject a plausible incomplete result, not just checks for absent warnings or old failures. Use `red-first.py --repo DIR --revision REV --tests DIR --junit REPORT -- COMMAND...` to prove each new test fails on the old revision in a disposable checkout. The test directory is overlaid in that checkout by its basename; use a report path relative to the checkout and select only the new tests. A missing report, setup error or passing test is not red evidence; a red baseline alone does not prove the checks cover the outcome.

Keep one small state object with goal, checklist, milestones, decisions and budget used. Write it atomically with `state.py --file FILE --data JSON`; keep evidence and approvals available to the user. Capture the checks baseline on the starting commit with `checks.py baseline --spec FILE --baseline FILE`, then use `compare` after changes. The spec is JSON with `commands`, each containing a unique `name`, an `argv` array and, for tests, a `junit` report path. Run commands from the project root; never overwrite the original baseline. Untracked and ignored files must be absent or listed explicitly under `allowed_untracked` and hashed, except for the narrow declarations below. Use a clean checkout to avoid inventorying unrelated files. If a test cannot produce usable JUnit evidence, disclose it and do not claim its count was verified.

For the active work, optionally set `work_states` to a list containing its exact project-relative `.aid/works/work-NNN-name/STATE.yml`; set `AID_STATE_FILE` and `AID_WORK_DIR` to that same file and directory. Its contents may change, with hashes recorded and reported; other tracked changes still prevent a baseline. For a linked dependency, optionally set `dependency_links` to objects with `path` (the project-relative link), `target` (its absolute resolved directory) and `lockfile` (a tracked project-relative lockfile). The helper checks the target, lockfile and dependency tree before and after checks. Keep writable caches outside that tree. Hashing records what was installed; it does not prove the tree matches the lockfile. Declarations use forward-slash project-relative paths and do not permit other unexpected files.

JUnit paths must be untracked, unlinked and initially absent. Keep the helper's `<baseline>.reports.json` receipt and reports intact for comparison; the helper will not delete an unknown or altered report. To compare an older baseline without a receipt, inspect and move its existing unowned report to a safe location first; the helper never removes it automatically. Comparing also requires the same starting commit, commands and stable inputs.

Work through milestones in the foreground. At each milestone run the checks and request the independent result review in `review.md`. At the end review the whole result and show the user the outcome, evidence, pre-existing failures and unresolved issues for approval.
